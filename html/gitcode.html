Quy cách đặt tên Repository

Dựa theo loại project - Tên repository nên phản ánh rõ loại dự án

Dựa vào loại, tên của project có thể đặt theo quy cách :

  • Web App: webpr-tên-dự-án
  • Android App: androidpr-tên-dự-án
  • Game gamepr-tên-game

Nếu là bài tập, các Exercise có thể đặt tên theo dạng ex-tên-môn-tên-bài:

  • ex-javapr-bt1
  • ex-pythonpr-bt2
  • ex-webpr-bt3
    • (Có thể gộp tất cả các project bài tập thành 1 Repository duy nhất như "ex-gamepr" và lưu tất cả các project dưới dạng mỗi folder con)

Quy cách đặt tên Branch (Nhánh)

Dựa theo nhiệm vụ của nhánh đó - Tên branch phản ánh được chức năng hoặc nhiệm vụ đang làm trên nhánh đó

  • Feature: feature/nên-chức-năng
  • Fix: fix/tên-vấn-đề
  • Modify: modify/tên-chức-năng
  • Style: style/tên
  • Document, README: docs/tên
  • Config, setup: chore/tên
  • Member: member/tên-thành-viên (có thể có hoặc ko)

Tạo file .gitignore

Tuỳ vào loại project - Tạo file .gitignore phù hợp với loại dự án để tránh commit các file không cần thiết

Các file cần được ignore có thể là:

  • File cấu hình IDE (ví dụ: .idea/)
  • File build (ví dụ: build/)
  • File log (ví dụ: *.log)
  • File tạm (ví dụ: *.tmp)
  • File nhạy cảm (ví dụ: .env)

Ví dụ luồng branch khi làm việc nhóm

Main là bản ổn định, develop là nơi gom code, mỗi member có nhánh riêng và tách tiếp các nhánh chức năng.

main
develop
feature/login-ui feature/validate-form
feature/student-list feature/search-student
feature/profile-page feature/update-score
Luồng merge: feature/* → member/* → develop → main

GitHub Teamwork Rules

Quy tắc teamwork khi làm việc nhóm với GitHub

Các nguyên tắc cơ bản giúp team tránh conflict, giữ code sạch và merge vào develop an toàn.

01

Các quy tắc bắt buộc khi teamwork

Thành viên không tự ý Merge trên remote
Không commit trực tiếp vào main
Mỗi người phải có branch riêng
Pull code mới nhất trước khi push
Commit message phải rõ nghĩa
Không sửa file người khác nếu chưa trao đổi
Không push code lỗi
Không để file rác trong project
Luôn kiểm tra conflict trước khi merge
Hoàn thành task nhỏ rồi mới commit
Không rename file lung tung
Không tự ý xoá code người khác
Tạo Pull Request trước khi merge vào develop
02

Quy tắc đặt commit message

feat(scope): add login UI

feat dùng khi thêm chức năng mới.

fix(scope): validate email

fix dùng khi sửa lỗi.

docs(scope): update README

docs dùng khi sửa tài liệu.

style(scope): update navbar color

style dùng khi chỉnh giao diện, format, màu sắc.

refactor(scope): clean code login service

refactor dùng khi làm sạch code nhưng không đổi chức năng.

03

Các lỗi teamwork thường gặp

2 người sửa cùng 1 file
Quên pull trước khi push
Push nhầm lên main
Commit quá nhiều file rác
Merge conflict
Không tạo branch riêng
Đặt tên branch lộn xộn
04

Workflow teamwork chuẩn

1Pull develop mới nhất
2Tạo branch feature
3Làm task riêng
4Commit code
5Push branch
6Tạo Pull Request
7Review code
8Merge vào develop
9Cả team pull lại develop
05

Mẹo teamwork tốt

Chia task rõ ràng
Tách component nhỏ
File nào sửa nhiều thì báo team
Commit nhỏ và thường xuyên
Đặt tên branch dễ hiểu
Trao đổi trước khi sửa logic chung

Clone Project

git clone https://github.com/your-project.git

Dùng để tải source code từ GitHub về máy.

Create Branch

git checkout -b feature/login

Tạo branch mới để làm feature riêng.

Add & Commit

git add .

git commit -m "Update UI"

Thêm file vào staging và commit code.

Push Code

git push origin feature/login

Đẩy code từ máy local lên GitHub.

Pull Latest Code

git pull origin develop

Cập nhật code mới nhất từ branch develop.
